# WAN から VLAN 経由で GUI にアクセスする設定 - 20260602

先へ進む前に、初期セットアップでも少し触れましたが、WAN（port1）からの HTTPS アクセスを無効化しておきたいと思います。
ただし、WAN側のIPアドレスでGUIにログインしたままこの設定を変更すると、その後GUIに再ログインできなくなります。
そのため、ここから先は LAN 側の IP アドレス経由で GUI にアクセスするようにします。

注： セキュリティを気にしない場合や、インターネット経由で GUI の管理アクセスを許可しても問題ない場合（ホームラボ用途なら許容できるかもしれませんが、本番環境では推奨しません）は、この手順をスキップしても構いません。<br>
その場合はport1のHTTPSアクセスを有効のままにしておいてください。

## ホームサーバー VLAN へのルーティング

ここは本当に何時間もトラブルシューティングに費やしました。<br>
正しい設定をしても別の部分が壊れたり、その修正をしたら今度は別の問題が出たりと、なかなか一直線には進みませんでした。<br>
それでも最終的には解決できました！<br>
できるだけ整理して、実際に効果があった設定や原因だったポイントをまとめています。<br>
もし同じ方法で解決しなくても、自力で切り分けが必要になるかもしれません。<br>
ただ、少なくとも問題へのアプローチ方法や、どのあたりを確認すべきかの参考にはなると思います。

### UFW（ホストファイアウォール）の設定

まずはファイアウォール側から確認します。<br>
すでにサーバーで UFW を設定している場合、既存の設定と競合している可能性があります。

現在の設定を確認します。<br>
`sudo iptables -L FORWARD -n -v`<br>
`Chain FORWARD (policy DROP)` が表示され、さらにLIBVIRT関連で `ufw-reject-forward all` が見える場合、明示的に許可された通信以外はすべて転送がブロックされている状態です。<br>
まずはこれを修正します。

最初に、UFW でフォワーディングを有効にします。<br>
`sudo nano /etc/ufw/sysctl.conf`<br>
`#net/ipv4/ip_forward=1` を探し、コメントアウトを解除（# を削除）します。保存して終了してください。<br>
次にデフォルト設定を変更します。<br>
`sudo nano /etc/default/ufw`<br>
`DEFAULT_FORWARD_POLICY="DROP"` を探し、`DROP` を `ACCEPT` に変更します。保存して終了してください。<br>
続いて、br0 と virbr-lan 間の通信を許可します。<br>
```
sudo ufw route allow in on br0 out on virbr-lan
sudo ufw route allow in on virbr-lan out on br0
```

最後に UFW を再読み込みします。<br>
`sudo ufw reload`

### Libvirt（VM 管理ツール）の設定

次は libvirt 側です。<br>
この問題は、libvirtに標準で組み込まれているネットワーク分離機能が原因です。デフォルトでは同じ仮想ネットワーク内の通信（例: virbr-lan → virbr-lan）のみ許可し、それ以外との通信は遮断する設計になっています。通常の用途では便利な機能ですが、今回やりたい構成には向いていません。<br>
そのため、libvirtのネットワーク定義を編集してフォワーディングを有効にします。<br>
ネットワークのForward Modeを「isolated」から「route」に変更します。<br>
`virsh net-edit vnet-lan`

エディタ選択画面が表示されたら、一番上のエディタを選択してください。<br>
その後、以下を追加します。<br>
`<forward mode='route'/>`

![alt text](images/fortigate-wan-to-vlan/forwardmode.png)

変更を反映するため、ネットワークを再起動します。<br>
```
virsh net-destroy vnet-lan
virsh net-start vnet-lan
```

続いて `bridge link show` を実行し、vnet1 が表示されているか確認します。<br>
もし表示されていなければ、以下で再接続します。<br>
`sudo ip link set vnet1 master virbr-lan`<br>
さらに `virsh domiflist fortigate` を実行し、再起動後も設定が維持されることを確認してください。<br>
vnet1 の Type が `network`、Source が `vnet-lan` になっていれば問題ありません。

### Netplan の設定

私の環境では、ここで 2 つの修正が必要でした。<br>
そのうち 1 つはかなり環境依存です。<br>

1. Wi-Fi の IP アドレスがブリッジ通信と競合していた
2. ブリッジ側にルーティング設定が必要だった

1. FortiGate の LAN IP に対して ping が通らない問題が残っていました。原因は非対称ルーティング（Asymmetric Routing）だったようです。<br>
通信は一方の経路から入り、応答が別の経路から返っていました。Wi-Fi とブリッジが同じルートを使っていたため、Netplan から静的 IP 設定を削除しました。もし FortiGate の LAN IP に ping を送った際に "Request timed out" が返る場合は、Netplan から Wi-Fi の `addresses`、`routes`、`nameservers` を削除してみてください。私のように初期セットアップ時に Wi-Fi 用 Netplan を構成していなければ、この問題は発生しないはずです。ちなみに現在は Wi-Fi ではなく、有線（eno1 の IP アドレス）経由で SSH 接続しています。<br>

2. 次にデフォルトルートを追加し直しました。<br>
`sudo ip route add default via 192.168.x.x dev br0`<br>
さらに Netplan にも同じ内容を追加して永続化します。基本的には、以前 Wi-Fi 側で設定していた内容を br0 に移したイメージです。なお、上記コマンドの IP アドレスと、下図のroute設定に使用するIPアドレスは同じです（デフォルトゲートウェイ）。`addresses` に指定する IP はホームサーバー自身の IP アドレスになります。<br>
![alt text](images/fortigate-wan-to-vlan/netplan.png)

### port2 の RPF（Reverse Path Forwarding）を無効化する

続いて FortiGate コンソールから port2 の RPF を無効化します。<br>
問題となっているのは、FortiGate のセキュリティ機能のひとつです。<br>
パケットを受信すると、その送信元へ戻る経路が同じインターフェースかどうかを確認します。<br>
今回のケースでは、パケットは PC の IP アドレスからport2に到着しています。<br>
しかしFortiGateのルーティングテーブルでは、その IP アドレスへ到達するには port1 を使用すると判断しています。<br>
受信インターフェースとルーティング結果が一致しないため、FortiGateは送信元 IP が偽装されていると判断し、パケットを破棄します。<br>
ルーティングテーブルを変更して対処することもできますが、その場合はPC側を固定IPにする必要があります。DHCPではうまく動きません。<br>

IP スプーフィング対策を無効化するので不安に感じるかもしれませんが、port2は内部 LAN です。<br>
port2 にパケットを送れるのは、私たちが管理している virbr-lan 上の VM のみです。<br>
ただし、port1（WAN）側の RPF 保護は必ず有効のままにしておきましょう。

私はDHCP構成を変更したくなかったため、この機能を無効化する方法を選びました。<br>
`sudo virsh console fortigate`<br>
でコンソールに入り、ログイン後に以下を実行します。<br>
```
config system interface
    edit port2
        set src-check disable
    next
end
```

### IP Forwarding

次に、KVM ホスト（ハイパーバイザー）で IP Forwarding を有効化します。<br>
これにより、ホームネットワーク（PC が接続されている側）と virbr-lan の間で通信を中継できるようになります。<br>
永続化するため、新しい sysctl 設定ファイルを作成します。<br>
```
echo "net.ipv4.ip_forward=1" | sudo tee /etc/sysctl.d/99-ipforward.conf
sudo sysctl -p /etc/sysctl.d/99-ipforward.conf
```

### ルーティング設定

最後に、PC側へ静的ルートを追加します。<br>
これによりVLANネットワークへアクセスする際はKVMホスト経由で通信するようになります。<br>
Windowsの場合は、管理者権限のコマンドプロンプトで以下を実行してください（Mac は設定方法が異なります）。<br>
`route add 10.x.x.x mask 255.255.255.0 192.168.x.x -p`<br>
→ `-p` を付けることで再起動後も設定が保持されます。<br>
→ 最後のIPアドレスはKVMホストの固定IPアドレスです。<br>
設定後、VLAN側のIPアドレスでGUIにアクセスできるか確認します。<br>
`https://10.x.x.x/login`

※ セキュリティ警告を無視してログイン画面へ進んだあと、表示されるまでかなり時間がかかる場合があります。<br>
正直なところ原因はよく分かっておらず、ルーティング関連かもしれません。<br>
接続できないと表示されても、そのままページを開いた状態で待ってみてください。<br>
サーバーへの ping が正常に通っているのであれば、最終的に表示されることがあります。

※ それでも GUI に接続できない場合は、PCからVLAN IP にpingを送ってみてください。<br>
応答内容を見ることで、ファイアウォールポリシーの問題なのか、ルーティングの問題なのかを切り分けやすくなります。<br>
もし応答元がVLAN IPではなくPC自身のIPアドレスになっている場合は、PC側のルーティング設定が原因である可能性が高いです。<br>
その場合は静的ルートを再設定してみてください。<br>

正常な場合は対象 IP から応答が返っていますが、異常な場合は PC 自身の IP アドレスから応答が返っていることが分かります。
